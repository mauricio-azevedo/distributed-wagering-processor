# Glossary

Terms used across the documentation and the code. When a term appears in a rule of the [system contract](system-contract.md), it has the meaning given here.

| Term                 | Meaning                                                                                                                                                                                                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Provider             | A game provider integration that submits operations. Identified by `providerId`. The value `system` is reserved for transactions the service creates itself.                                                                                                              |
| Player               | The end user who owns wallets. Identified by `playerId`, a UUID minted by the platform.                                                                                                                                                                                   |
| Wallet               | The aggregate root: one per player and currency. Holds the materialized balance and the version.                                                                                                                                                                          |
| Round                | A game round grouping a bet with its outcome and its reversals. Identified by `roundId` within a provider.                                                                                                                                                                |
| Game                 | The game a round belongs to. Identified by `gameId` within a provider; informational.                                                                                                                                                                                     |
| Operation            | One provider request against a wallet: `BET`, `WIN`, `LOSS`, `REFUND` or `ROLLBACK`.                                                                                                                                                                                      |
| Transaction          | The persisted record of an operation, or of the internal `OPENING` credit. Has a kind, a status and, once recorded, an outcome.                                                                                                                                           |
| Kind                 | `BET` debits a stake; `WIN` credits a payout; `LOSS` records an outcome without moving money; `REFUND` returns a bet; `ROLLBACK` reverses a processed transaction; `OPENING` credits a wallet's initial balance.                                                          |
| Status               | `PENDING` (accepted, not yet applied), `PENDING_REFERENCE` (waiting for the referenced transaction), `PROCESSED`, `REJECTED`, `FAILED`. The last three are terminal.                                                                                                      |
| Terminal status      | A status that never changes again: `PROCESSED`, `REJECTED` or `FAILED`.                                                                                                                                                                                                   |
| Outcome              | What a submission produced: the transaction id, its status, the failure code when rejected or failed, the observed balance, and whether the response is a replay.                                                                                                         |
| Observed balance     | The wallet balance at the moment an outcome was recorded. Frozen with the outcome and returned on every replay.                                                                                                                                                           |
| Ledger entry         | The immutable record of one balance change: direction, amount, balance before and after, and the wallet version it produced.                                                                                                                                              |
| Ledger head          | The entry of a wallet with the greatest wallet version. The wallet row mirrors it at commit; every other entry is continued by the next one.                                                                                                                              |
| Wallet version       | Counter starting at 1 when the wallet is created and incremented once per balance change. Also the per-wallet sequence of ledger entries and the ordering key of the ledger.                                                                                              |
| Direction            | `DEBIT` removes money from the wallet; `CREDIT` adds money.                                                                                                                                                                                                               |
| Reference            | The provider transaction an operation points at through `referenceExternalTransactionId`. Required for `REFUND` and `ROLLBACK`, optional for `WIN` and `LOSS`, forbidden for `BET`.                                                                                       |
| Reversal             | A `REFUND` or a `ROLLBACK`: an operation that undoes a processed transaction, once.                                                                                                                                                                                       |
| Pending reference    | A transaction parked because its reference has not been processed yet; retried with backoff for a bounded window, then rejected.                                                                                                                                          |
| Business fields      | `providerId`, `externalTransactionId`, `playerId`, `walletId`, `roundId`, `gameId`, `kind`, `money` and the optional `referenceExternalTransactionId`. The HTTP request body, the `data` of a queue message (plus the idempotency key) and the input of the payload hash. |
| External identifier  | An id minted outside the service: `providerId`, `externalTransactionId`, `roundId`, `gameId`. 1 to 120 characters from `A-Z a-z 0-9 . _ : -`, starting with a letter or digit.                                                                                            |
| Idempotency key      | Caller-chosen key that identifies one operation per provider. Mandatory. Recommended value `{providerId}:{externalTransactionId}`.                                                                                                                                        |
| Payload hash         | SHA-256 of the canonical JSON of the business fields; detects a key reused with a different payload.                                                                                                                                                                      |
| Replay               | A request whose idempotency key and payload hash match a stored transaction. Returns the stored outcome without any effect.                                                                                                                                               |
| Failure code         | Stable, machine-readable reason carried by a `REJECTED` or `FAILED` transaction.                                                                                                                                                                                          |
| Error code           | Stable, machine-readable reason carried by a request-level error (`400`, `404`, `409`, `503`); nothing is persisted.                                                                                                                                                      |
| Entry point          | A way operations reach the service: HTTP (`POST /wagering/transactions`) or the queue (`wager-transactions.fifo`). Both run the same use case.                                                                                                                            |
| Inbox                | Persistent record of consumed queue messages, keyed by consumer name and message id; absorbs redeliveries.                                                                                                                                                                |
| Outbox               | Persistent record of integration events written in the same database transaction as the financial change; a publisher relays them to the broker after commit.                                                                                                             |
| Integration event    | A fact published for other systems: `WagerTransactionProcessed`, `WagerTransactionRejected`, `WalletBalanceChanged`, `WagerTransactionPendingReference`. Delivered at least once with a stable `eventId`.                                                                 |
| Dead-letter queue    | `wager-transactions-dlq.fifo`: where messages go after a permanent failure or after exhausting their receives.                                                                                                                                                            |
| Correlation id       | Identifier that follows one request or message through logs and events. Taken from the caller when given, generated otherwise.                                                                                                                                            |
| Causation id         | On an event, the id of the transaction whose processing produced it.                                                                                                                                                                                                      |
| Reconciliation       | Comparison of a wallet's stored balance with the balance rebuilt from its ledger. Reports divergences; never corrects them.                                                                                                                                               |
| Instance role        | `api` serves HTTP; `worker` runs the queue consumer, the outbox publisher and the pending-reference scheduler; `all` runs both. Any number of instances of each role run at once.                                                                                         |
| Materialized balance | The balance stored on the wallet row, kept equal to the balance derivable from the ledger.                                                                                                                                                                                |
| Balance bound        | `999999999999999999.99`, the largest value a money column stores. Every `Money` value is inside it; a credit that would cross it is rejected with `BALANCE_LIMIT_EXCEEDED`.                                                                                               |
| Transport contract   | `docs/openapi.yaml` for HTTP and `docs/asyncapi.yaml` for the queues: the authoritative definition of every request, response, message, event, header, status code and delivery semantic. The code implements them.                                                       |
